# M3: generated partner clients

**Declared:** 2026-11-03 (Day 23). **Data:** every OpenAPI spec (3 dev, 3 test); HX is HTML and has no
schema to check against. **No LLM** (ADR-001 §6): the client is written from templates.

## What M3 is

Labels say which partner field carries which canonical field, and how. M3 turns a spec's labels into
plain, readable Python that does the wiring in both directions, and checks it against the partner.

```
labels ─► plan.py ─► generate.py ─► client_<partner>.py ─► from_… : partner response ─► canonical record
(any:      steps;     templates,      uses runtime.py          ─► to_…   : canonical booking ─► partner request
gold or    NONE       no LLM          (get, put, the 7
predicted) dropped                    vocabulary transforms)
                                                    integration.to_booking: + padan's own fields ─► Booking
```

- **`derived` and `ask` are never guessed.** Each becomes a `# TODO` line in the code and an entry in
  the module's `TODOS` list: escalation, visible in code.
- **Only exact reverses are used for requests:** enum maps (our value back to the partner's code),
  minor units, and copies. A date part cannot rebuild the partner's date-time alone, so it is a TODO.
- **Unknown codes fail loudly** (`enum_map` raises); casting to the partner's types reshapes only what
  it can reshape exactly, and leaves the rest for the schema check to name.
- **Padan-owned fields** come from `integration.to_booking`: padan's own booking ID, the vertical it
  sells, and, when the partner flags none, the lead traveller (the one whose name matches the contact,
  else the first). Every choice is returned as a note.

## Method

- **Requests:** one sample booking (two travellers, one item, a price) through every `to_…` function;
  each body is validated against the partner's own request schema with jsonschema. Problems are sorted
  into *missing* required fields, wrong *types*, and *other*.
- **Responses:** every example response in the spec through `from_…` and `to_booking`; the result must
  be a valid `Booking`.
- **Two label sources:** the gold (the corrected copy for test specs) and the frozen system's
  predictions (Day 11 on dev, Day 16 on test). Run with `make m3`; results in `docs/results/m3/`.

## What the numbers say

1. **The generator gives the same outcome from human gold and from model predictions.** Viator's
   create request is valid against Viator's own schema from both; everywhere else both fail on the same
   fields.
2. **Every remaining failure is named, and of three kinds**, each with an owner:
   - **fields the partner requires that padan's schema does not hold** (Hotelbeds' holder address and
     mailing preferences; Musement's quantity and type; GetYourGuide's payment and country code): the
     schema's scope, or a per-partner constant;
   - **TODOs** (OCTO's unit IDs, Headout's price, GetYourGuide's categories and date-time): a person,
     with the partner's answer;
   - **data the example does not contain** (OCTO's example has no traveller names; Viator's status
     example has no contact, items or status): nothing padan can fill.
3. **The fourth kind found on Day 22, types, is fixed** by casting to the partner's schema types.
4. **Predicted labels differ in shape, not outcome:** the system never writes `derived` (its reply
   has map, none and ask), so its TODOs are all asks; it uses many more transforms on GetYourGuide.

## Limitations

- **One sample booking.** Its catalogue IDs are digits kept as text (`1001`, `2002`), as many partners
  issue them; a partner with text IDs would still accept them.
- **Lists:** values are flattened when read and filled element by element when written (the first list
  level into a canonical record, the last into a partner request). Bookings with several items whose
  travellers differ per item are not modelled.
- **Few examples:** only OCTO and Viator ship example responses, so the response side is measured on two
  bodies.
- **Schemas, not servers:** a request the schema accepts can still be refused by the partner's business
  rules. No partner API was called.
