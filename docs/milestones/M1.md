# M1: rule engine, measured on dev

**Declared:** 2026-10-23 (Day 9, as planned on Day 4). **Data:** the 4 dev specs only; the test specs
have not been opened.

## What M1 is

A deterministic mapper from a partner's booking fields to padan's canonical booking schema (v3). For
every field it decides one of three things: map it (with a transform where needed), leave it blank
(`NONE`), or ask the partner (`ASK_PARTNER`) when a critical meaning is not documented. No LLM is used.

```
partner docs ─► Stage 1 extraction ─► candidate finder ─► decide() ─► R4 enum maps ─► label file
                (fields + evidence)   tokens, lexicon,     escalation   documented     scored against
                                      context              policy       values         gold labels
```

## Method

- **Leave-one-spec-out (LOSO).** Every lexicon entry records the dev specs it was learnt from. When a
  spec is scored, entries learnt only from that spec are switched off, so each score is the rules'
  performance on a partner they were not written for.
- **Two variants.** *Strict* uses only words learnt from other dev specs, widened contexts and the
  schema's own field names. *General* adds 33 hand-written synonym entries; their author had read the dev
  specs, so this number is optimistic. Strict is the floor, general the ceiling, and the untouched
  test set decides.
- **Scoring** (decisions S1–S7, Day 6): mapping precision, recall and F1 over canonical pairs (macro
  over specs is the headline); escalation precision and recall over `ASK_PARTNER`; transform accuracy;
  and **silent critical errors**, a wrong value written into a critical field without a question.

## What the numbers say

- **Rules are precise and narrow.** Precision 0.84–0.96; recall 0.27–0.45. Under LOSO the candidate
  finder proposes the right target for only 26% (strict) / 48% (general) of gold pairs, and `decide()`
  converts nearly all of those. The limit is vocabulary, not the decision policy.
- **Memorisation is real and measured.** With a spec's own entries on, candidate recall is 93%; with
  them off, 26%. Only 4 of 78 drafted entries were taught by more than one partner.
- **The escalation policy prevents silent errors.** Strict's 3 critical errors are all Headout
  currency fields mapped to the gross price by a rule HX taught; HX's docs say gross, Headout's do not
  say. Where both gross and net are proposed, `decide()` asks instead, which is why general has 0.

## Known gaps (carried into M2)

| Gap | Size on dev | Why not fixed in M1 |
| --- | --- | --- |
| Words taught by one partner only (e.g. OCTO `deliveryFormat`) | most of the 67 misses (general) | Needs language understanding, or more partners: M2 |
| `status` codes (lifecycle enums) | 2 pairs asked instead of mapped | Same code, different meaning: Headout `PENDING` means *confirmed*. A name match would be a silent critical error; M2 reads per-value descriptions |
| Keyed fields (`inputFields[id=EMAIL].value`) | 11 Headout pairs | One dev example cannot be validated under LOSO; designed in M2 if the pattern recurs |
| Derived values (counts, lookups, conditional expiry) | 5 pairs | Not learnable from names |
| Values listed only in a schema `enum` (Headout `tickets[].type`) | 1 field | Stage 1 keeps descriptions, not `enum` lists |
| HX amounts under several price nodes | 3 fields asked, gold `NONE` | Accepted: asking is the safe failure |

**Limitations of the evaluation:** one labeller (a 20% second-labeller sample is planned before
results are published); dev gold for OCTO and HX was model-drafted and human-reviewed; the general
synonyms were not written blind.
